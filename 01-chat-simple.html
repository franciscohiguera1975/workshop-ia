Módulo 01 — Creando la API base: Chat simple

Objetivo: construir, desde una carpeta vacía, un backend FastAPI real — primero un endpoint de salud, después un endpoint /chat que habla con un LLM — entendiendo cada pieza que agregamos.

Herramientas: FastAPI, Uvicorn, el SDK openai (apuntado a cualquier proveedor compatible).

Prerequisito: Módulo 00 (Python/Node instalados, proveedor elegido).

1.1 Crear el proyecto

mkdir -p backend/app/routers
cd backend
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate

1.2 Instalar dependencias

Crea backend/requirements.txt:

fastapi
uvicorn[standard]
openai
python-dotenv
pydantic
pip install -r requirements.txt

1.3 Tu primer endpoint: GET /health

Crea backend/app/__init__.py (vacío — convierte app en un paquete de Python) y backend/app/main.py:

from fastapi import FastAPI

app = FastAPI(title="Workshop IA — Backend")


@app.get("/health")
def health():
    return {"status": "ok"}

Levántalo:

uvicorn app.main:app --reload --port 8000

Pruébalo:

curl -s http://localhost:8000/health
# {"status":"ok"}

Abre también http://localhost:8000/docs — FastAPI genera esa interfaz (Swagger UI) automáticamente a partir de tu código, sin que escribas nada extra. La vas a usar el resto del taller para probar endpoints sin salir del navegador.

1.4 Habilitar CORS

El frontend corre en http://localhost:5173 y el backend en http://localhost:8000 — son orígenes distintos, así que el navegador bloquea la llamada por defecto. Agrega esto a main.py:

from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI(title="Workshop IA — Backend")

app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_methods=["*"],
    allow_headers=["*"],
)


@app.get("/health")
def health():
    return {"status": "ok"}

(allow_origins=["*"] es solo para el taller — en producción se restringe a los dominios reales.)

1.5 Configuración por entorno

Antes de hablar con un LLM, necesitamos saber a cuál — y eso no va escrito en el código, va en variables de entorno.

Crea backend/.env.example:

# Copiar a .env y completar. Nunca commitear .env con claves reales.
# Elegir proveedor: vllm | groq | openai (ver Módulo 00 §0.2)
LLM_PROVIDER=groq
LLM_BASE_URL=https://api.groq.com/openai/v1
LLM_API_KEY=
LLM_MODEL=llama-3.3-70b-versatile
cp .env.example .env

Crea backend/app/config.py:

import os
from dataclasses import dataclass

from dotenv import load_dotenv

load_dotenv()


@dataclass
class Settings:
    llm_provider: str
    llm_base_url: str
    llm_api_key: str
    llm_model: str


def get_settings() -> Settings:
    return Settings(
        llm_provider=os.getenv("LLM_PROVIDER", "groq"),
        llm_base_url=os.getenv("LLM_BASE_URL", "https://api.groq.com/openai/v1"),
        llm_api_key=os.getenv("LLM_API_KEY", ""),
        llm_model=os.getenv("LLM_MODEL", "llama-3.3-70b-versatile"),
    )

Nada se hardcodea: cambiar de proveedor en todo el taller va a ser cambiar 4 líneas de .env y reiniciar uvicorn — nunca tocar código.

1.6 El cliente del LLM (el adaptador)

Esta pieza aísla “cómo le hablo a un modelo” del resto de la aplicación. Crea backend/app/llm_client.py:

from openai import OpenAI

from .config import get_settings


class OpenAICompatibleClient:
    """Sirve para vLLM local, Groq y la API de OpenAI (ChatGPT): los tres
    exponen la misma API — solo cambian base_url/api_key/model. Por eso un
    único cliente alcanza para los tres (y para cualquier otro proveedor
    que hable el mismo protocolo, ver Módulo 00 §0.2)."""

    def __init__(self, base_url: str, api_key: str, model: str):
        self._client = OpenAI(base_url=base_url, api_key=api_key)
        self._model = model

    def chat(self, messages: list[dict]) -> str:
        response = self._client.chat.completions.create(
            model=self._model, messages=messages
        )
        return response.choices[0].message.content or ""


def get_llm_client() -> OpenAICompatibleClient:
    settings = get_settings()

    if not settings.llm_api_key:
        raise RuntimeError(
            "Falta LLM_API_KEY en backend/.env — ver Módulo 00 §0.2 para "
            "obtener una clave de Groq, OpenAI o tu proveedor elegido."
        )

    return OpenAICompatibleClient(
        settings.llm_base_url, settings.llm_api_key, settings.llm_model
    )

Pruébalo aislado, antes de conectarlo a HTTP — es una buena práctica: verificar una pieza por separado antes de montarla sobre FastAPI.

python3 -c "
from app.llm_client import get_llm_client
client = get_llm_client()
print(client.chat([{'role': 'user', 'content': 'Hola'}]))
"

Deberías ver una respuesta real del modelo que configuraste en .env. Si ves un RuntimeError sobre LLM_API_KEY, revisa el Módulo 00 §0.2 y tu .env.

1.7 Tu segundo endpoint: POST /chat

Ahora sí, el endpoint que usa el cliente. Crea backend/app/routers/__init__.py (vacío) y backend/app/routers/chat.py:

from fastapi import APIRouter
from pydantic import BaseModel

from ..llm_client import get_llm_client

router = APIRouter()


class Message(BaseModel):
    role: str
    content: str


class ChatRequest(BaseModel):
    message: str
    history: list[Message] = []


class ChatResponse(BaseModel):
    reply: str


@router.post("/chat", response_model=ChatResponse)
def chat(request: ChatRequest) -> ChatResponse:
    client = get_llm_client()

    messages = [{"role": m.role, "content": m.content} for m in request.history]
    messages.append({"role": "user", "content": request.message})

    reply = client.chat(messages)
    return ChatResponse(reply=reply)

ChatResponse por ahora solo trae reply — en los Módulos 02, 03 y 04 le vamos a ir agregando campos opcionales (skill_used, sources, tool_calls) a medida que el backend gane esas capacidades. El frontend ya está preparado para eso: los muestra solo cuando existen.

Conéctalo en backend/app/main.py (agrega el import y la línea include_router):

from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

from .routers import chat

app = FastAPI(title="Workshop IA — Backend")

app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_methods=["*"],
    allow_headers=["*"],
)

app.include_router(chat.router)


@app.get("/health")
def health():
    return {"status": "ok"}

--reload ya debería haber recargado el servidor solo. Pruébalo:

curl -s http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "Explícame qué es una API en una frase", "history": []}' \
  | python3 -m json.tool

Deberías recibir {"reply": "..."}.

1.8 Pruébalo también en el frontend

  1. Confirma que npm run dev del Módulo 00 sigue corriendo (si lo cerraste, cd frontend && npm run dev) y abre http://localhost:5173.
  2. Escribe en el campo de texto: Explícame qué es una API en una frase y dale Enviar.
  3. Debe aparecer una burbuja de respuesta del asistente con texto del modelo (no un error).

Todavía no debe aparecer ningún enlace “Ver proceso” debajo de la burbuja — recién aparece desde el Módulo 02, cuando reply deja de ser el único campo de la respuesta. Si ves un error en la burbuja o en la consola del navegador, revisa que VITE_API_URL en frontend/.env apunte a http://localhost:8000 y que uvicorn siga corriendo.

1.9 Ejercicio 1 — cambia el tono con un system prompt (5 min)

Agrega un mensaje system fijo al inicio de messages en chat():

messages.insert(0, {"role": "system", "content": "Responde siempre en tono muy formal y en máximo 2 líneas."})

Prueba de nuevo y nota cómo cambia el tono sin tocar el modelo ni el proveedor. Déjalo o quítalo como prefieras — en el Módulo 02 reemplazamos esta idea por algo más potente: elegir el system prompt automáticamente según lo que pida el usuario (eso son las Skills).

1.10 Ejercicio 2 — comprueba que la “memoria” es responsabilidad del cliente (10 min)

El backend es stateless: no guarda nada entre requests. Toda la “memoria” de la conversación vive en el arreglo history que manda quien llama al endpoint. Compruébalo a mano, con dos llamadas seguidas por curl:

# 1) Le decimos cómo nos llamamos
curl -s http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "Me llamo Ana. Recuérdalo.", "history": []}' | python3 -m json.tool

Copia la respuesta (reply) que te dio, y mándala de vuelta como parte del history en la siguiente llamada:

curl -s http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{
    "message": "¿Cómo me llamo?",
    "history": [
      {"role": "user", "content": "Me llamo Ana. Recuérdalo."},
      {"role": "assistant", "content": "PEGA_AQUI_LA_RESPUESTA_ANTERIOR"}
    ]
  }' | python3 -m json.tool

Debería responder “Ana”. Ahora repite la segunda llamada pero con "history": [] (vacío) — el modelo ya no sabe tu nombre. Esto confirma algo importante para el resto del taller: si el frontend no mandara el historial completo en cada mensaje, no habría memoria en absoluto. Abre frontend/src/App.tsx y busca dónde arma history antes de cada sendMessage para ver cómo lo resuelve.
