Módulo 03 — RAG (Retrieval-Augmented Generation)

Objetivo: que el modelo responda usando documentos que tú le diste, no solo lo que aprendió en su entrenamiento — usando una base de datos vectorial real, no una simulación hecha a mano.

Herramientas: LanceDB (motor vectorial embebido — sin servidor que levantar) + el SDK openai para los embeddings (mismo patrón que ya usas para el chat).

Prerequisito: Módulo 02.

3.1 La idea en 3 pasos

  1. Guardas documentos (texto plano) en una base de datos vectorial.
  2. Cuando llega una pregunta, le pides a la base que busque los documentos semánticamente más parecidos (retrieval) — esto requiere convertir texto a vectores (embeddings), no solo contar palabras.
  3. Metes esos fragmentos en el prompt antes de preguntarle al modelo (augmented generation).

Usamos LanceDB porque es embebido (como SQLite, pero para vectores: un archivo en disco, sin proceso servidor) y porque trae soporte nativo para calcular embeddings él mismo — nuestro código no llama a ningún SDK de embeddings a mano, solo configura con qué calcularlos. Es, además, la misma base vectorial que usa un proyecto real construido con este patrón (Groq/OpenAI/vLLM para el modelo, LanceDB para el almacenamiento).

# --- vLLM local: necesitas un SEGUNDO servidor sirviendo un modelo de

# EMBEDDING_PROVIDER=vllm

# EMBEDDING_API_KEY=EMPTY

Si en el Módulo 00 elegiste Groq o vLLM para el chat, necesitas igual una clave de OpenAI solo para este endpoint de embeddings (Groq no los ofrece). Alternativas dedicadas a embeddings con capa gratuita: Voyage AI (mejor calidad, pero el registro pasa por una cuenta de MongoDB Atlas) o Jina AI (registro directo, cuota más chica) — ambas requieren su propia clase de embeddings en lancedb.embeddings, distinta a la de abajo; no se cubren en este módulo por tiempo.

3.4 El adaptador de embeddings: backend/app/embeddings.py

Esta es la única pieza “manual”: una función de embeddings que LanceDB va a usar automáticamente. Llama a cualquier endpoint compatible con OpenAI — igual que llm_client.py, pero para /embeddings en vez de /chat/completions — por eso sirve tanto para OpenAI como para un modelo de embeddings servido con vLLM.

from typing import List, Union

from lancedb.embeddings import TextEmbeddingFunction, register
from lancedb.embeddings.registry import get_registry


@register("openai_compatible_embeddings")
class OpenAICompatibleEmbeddings(TextEmbeddingFunction):
    """Embeddings reales vía cualquier endpoint compatible con OpenAI
    (la API de OpenAI, o vLLM sirviendo un modelo de embeddings)."""

    name: str
    base_url: str
    api_key: str
    dim: int = 1536

    def ndims(self) -> int:
        return self.dim

    def generate_embeddings(self, texts: Union[List[str], "np.ndarray"]) -> List[list]:
        from openai import OpenAI

        client = OpenAI(base_url=self.base_url, api_key=self.api_key)
        response = client.embeddings.create(model=self.name, input=list(texts))
        return [d.embedding for d in response.data]


def get_embedding_function():
    from .config import get_settings

    settings = get_settings()
    registry = get_registry()

    return registry.get("openai_compatible_embeddings").create(
        name=settings.embedding_model,
        base_url=settings.embedding_base_url,
        api_key=settings.embedding_api_key,
        dim=settings.embedding_dim,
    )

3.5 La base vectorial: backend/app/rag.py

Aquí está la parte importante: no hay ningún código nuestro que calcule un vector. Definimos un esquema (Document) donde text es el campo fuente y vector se calcula solo; add() y search() reciben texto plano y LanceDB hace el resto.

import lancedb
from lancedb.pydantic import LanceModel, Vector

from .embeddings import get_embedding_function

_embedding_fn = get_embedding_function()


class Document(LanceModel):
    title: str
    text: str = _embedding_fn.SourceField()
    vector: Vector(_embedding_fn.ndims()) = _embedding_fn.VectorField()


_db = lancedb.connect("./storage/lancedb")
_table = _db.create_table("documents", schema=Document, exist_ok=True)


def add_document(title: str, text: str) -> None:
    _table.add([{"title": title, "text": text}])


def list_documents() -> list[dict]:
    return [{"title": r["title"], "text": r["text"]} for r in _table.to_arrow().to_pylist()]


def search(query: str, top_k: int = 2) -> list[dict]:
    if _table.count_rows() == 0:
        return []
    results = _table.search(query).limit(top_k).to_list()
    return [
        {"title": r["title"], "text": r["text"], "score": round(1 / (1 + r["_distance"]), 3)}
        for r in results
    ]

./storage/lancedb es una carpeta (no un servidor): ahí quedan los archivos de la base vectorial, igual que un archivo .sqlite.

3.7 Usa RAG dentro de /chat

@router.post("/chat", response_model=ChatResponse)
def chat(request: ChatRequest) -> ChatResponse:
    client = get_llm_client()
    messages = [{"role": m.role, "content": m.content} for m in request.history]

    skill = select_skill(request.message)
    skill_used = None
    if skill:
        messages.insert(0, {"role": "system", "content": skill["instructions"]})
        skill_used = SkillUsed(
            name=skill["name"],
            reason=f'Se detectaron las palabras clave de "{skill["name"]}" en tu mensaje.',
        )

    retrieved = rag.search(request.message)
    sources = None
    if retrieved:
        context = "\n\n".join(f'[{d["title"]}] {d["text"]}' for d in retrieved)
        messages.insert(0, {
            "role": "system",
            "content": f"Usa el siguiente contexto si es relevante. Si no, ignóralo.\n\n{context}",
        })
        sources = [Source(title=d["title"], snippet=d["text"], score=d["score"]) for d in retrieved]

    messages.append({"role": "user", "content": request.message})
    reply = client.chat(messages)

    return ChatResponse(reply=reply, skill_used=skill_used, sources=sources)

3.10 Ejercicio 2 — por qué el chunking importa (15 min)

Hasta ahora cada documento es un párrafo corto — un caso fácil. En la vida real un documento mide páginas, y cargarlo completo como una sola fila hace que la búsqueda sea imprecisa: el vector representa “todo el documento” en promedio, no la frase puntual que te interesa.

Compruébalo. Carga este “documento largo” como un solo registro:

curl -s http://localhost:8000/documents \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Manual del empleado (completo)",
    "text": "Horario: la jornada es de 8:00 a 17:00 con una hora de almuerzo. Vacaciones: los empleados tienen derecho a 15 días hábiles de vacaciones al año, acumulables hasta por 2 años. Teletrabajo: se permite hasta 3 días a la semana con aprobación del jefe directo. Viáticos: se reembolsan contra factura, hasta 30 días después del viaje."
  }'

Pregunta por los viáticos:

curl -s http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "¿Hasta cuándo tengo para presentar mis facturas de viaje?", "history": []}' \
  | python3 -m json.tool

LanceDB persiste en disco (./storage/lancedb), así que ese documento sigue ahí aunque reinicies uvicorn — no hace falta borrarlo para el ejercicio. Ahora carga el mismo contenido, pero dividido en 4 fragmentos, uno por tema (quedan en la misma tabla, junto al documento largo de arriba):

curl -s http://localhost:8000/documents -H "Content-Type: application/json" \
  -d '{"title": "Manual — Horario", "text": "La jornada es de 8:00 a 17:00 con una hora de almuerzo."}'
curl -s http://localhost:8000/documents -H "Content-Type: application/json" \
  -d '{"title": "Manual — Vacaciones", "text": "Los empleados tienen derecho a 15 días hábiles de vacaciones al año, acumulables hasta por 2 años."}'
curl -s http://localhost:8000/documents -H "Content-Type: application/json" \
  -d '{"title": "Manual — Teletrabajo", "text": "Se permite teletrabajo hasta 3 días a la semana con aprobación del jefe directo."}'
curl -s http://localhost:8000/documents -H "Content-Type: application/json" \
  -d '{"title": "Manual — Viáticos", "text": "Los viáticos se reembolsan contra factura, hasta 30 días después del viaje."}'

Repite la misma pregunta sobre viáticos y compara el campo sources de ambas respuestas: con el documento partido, sources trae el fragmento “Manual — Viáticos” con un score más alto y sin ruido de los otros temas — justo el fragmento que responde la pregunta, nada más.

Chunking es exactamente esto: dividir documentos largos en fragmentos de tamaño razonable (en producción, 300-500 palabras con algo de solapamiento entre fragmentos consecutivos) antes de cargarlos. El resto del flujo (search → contexto → sources) no cambia — lo único que cambia es cómo trozas el texto antes de llamar a add_document.

Instala pypdf (lee texto de PDFs) si no lo hiciste ya:

Crea backend/scripts/ingest_folder.py:

import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parent.parent))

from app import rag  # noqa: E402

DOCS_DIR = Path(__file__).resolve().parent.parent / "documents"
MAX_WORDS = 400


def read_text(path: Path) -> str:
    if path.suffix.lower() == ".pdf":
        from pypdf import PdfReader

        reader = PdfReader(str(path))
        return "\n".join(page.extract_text() or "" for page in reader.pages)
    return path.read_text(encoding="utf-8")


def chunk_text(text: str, max_words: int = MAX_WORDS) -> list[str]:
    words = text.split()
    return [" ".join(words[i : i + max_words]) for i in range(0, len(words), max_words)]


def main():
    if not DOCS_DIR.exists():
        print(f"No existe {DOCS_DIR} — créala y coloca ahí tu .txt o .pdf.")
        return

    archivos = [p for p in DOCS_DIR.iterdir() if p.suffix.lower() in (".txt", ".pdf")]
    if not archivos:
        print(f"{DOCS_DIR} está vacía — no hay .txt ni .pdf que cargar.")
        return

    for path in archivos:
        texto = read_text(path)
        fragmentos = chunk_text(texto)
        print(f"{path.name}: {len(texto.split())} palabras -> {len(fragmentos)} fragmentos")

        for i, fragmento in enumerate(fragmentos, start=1):
            rag.add_document(title=f"{path.stem} — parte {i}", text=fragmento)

    print("\nListo. Para ver los vectores resultantes: python scripts/inspect_embeddings.py")


if __name__ == "__main__":
    main()

Nota que reutiliza el mismo chunking de 3.10 (bloques de ~400 palabras), ahora automático en vez de manual — cada fragmento se vuelve un rag.add_document(...) igual que un documento normal.

Mira los vectores por dentro

Hasta ahora vector es un campo invisible — LanceDB lo calcula y lo usa, pero nunca lo viste. Agrega esto al final de backend/app/rag.py:

def inspect_vectors(limit: int = 5) -> list[dict]:
    """Para ver cómo queda un documento después de convertirlo a embeddings
    (dimensión real del vector + sus primeros valores), no para uso en /chat."""
    rows = _table.to_arrow().to_pylist()[:limit]
    return [
        {
            "title": r["title"],
            "vector_dim": len(r["vector"]),
            "vector_preview": list(r["vector"][:8]),
        }
        for r in rows
    ]

Y crea backend/scripts/inspect_embeddings.py:

import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parent.parent))

from app import rag  # noqa: E402


def main():
    docs = rag.inspect_vectors(limit=10)
    if not docs:
        print("No hay documentos cargados todavía (usa /documents o scripts/ingest_folder.py).")
        return

    for d in docs:
        preview = ", ".join(f"{v:.4f}" for v in d["vector_preview"])
        print(f"- {d['title']!r}")
        print(f"    dimensiones: {d['vector_dim']}")
        print(f"    primeros valores: [{preview}, ...]")


if __name__ == "__main__":
    main()

Corre:

python scripts/inspect_embeddings.py

Vas a ver algo como:

- 'loei — parte 1'
    dimensiones: 1536
    primeros valores: [0.0123, -0.0456, 0.0789, ...]

Esto es literalmente lo que LanceDB guarda y compara con search(): un documento de texto se volvió una lista de 1536 números (con text-embedding-3-small; la dimensión depende de EMBEDDING_DIM). Ningún número individual “significa” algo por sí solo — lo que importa es que textos con significado parecido producen vectores cercanos entre sí (eso es justo lo que vuelve a aprovechar search() al buscar por similitud, en vez de por palabra exacta).

Si tu documento es muy largo (una ley completa puede ser cientos de fragmentos), ten en cuenta el costo/tiempo de generar tantos embeddings — para el taller, con 1-2 capítulos o las primeras páginas alcanza para ver el patrón.
